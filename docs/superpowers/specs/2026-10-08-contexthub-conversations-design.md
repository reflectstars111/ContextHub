# ContextHub：GitHub for AI Conversations

> 一个面向 AI 对话的开源版本控制平台，让任何人的高质量 AI 对话都可以被保存、共享、复用、Fork 和持续演化。

## 1. 已确认的产品边界

用户明确要求建设面向 AI 对话的开源版本控制平台，并确认首版通过“导入、粘贴已有对话，集中整理与分享”获取内容。

最新优先级：导入、导出、上传、下载必须足够方便，首先服务“我的 Codex 中有很多段对话，导出上传后，其他人下载并导入自己的 Codex”。该迁移闭环优先于社区展示、复杂版本协作和通用平台适配。具体证据与设计见 [Codex 迁移核查](../../research/2026-10-08-codex-portability.md)。

核心资产是对话及其上下文：人们如何提出问题、补充约束、比较方案，最终获得什么结论。这些过程应能被保留、发现、引用、复制、改编和共同维护。

首版主要服务普通 AI 用户：不用学习 Git、不需要 API Key，也能创建对话库并参与协作。平台源码开放、支持自行部署作为默认实现方向；源码许可在正式开源前确定。

平台不要求模型密钥来管理对话；下载者回到自己的 Codex 继续提问时，使用其自己的账号与环境。“导入为可继续使用的上下文”与“完整恢复原生会话状态”分别标记能力，不能混为一个已实现承诺。

首版只管理已经存在的对话，不接入模型调用，不提供平台内新聊，不包含 Agent 执行、工具托管、模型额度、计费或性能评测。后续是否增加新聊，由独立需求决定。

成功标准是陌生用户能够找到一段有用对话，理解其来龙去脉，复用到自己的工作，保存改编版本，并把改进贡献给原作者。

## 2. GitHub 概念如何对应

| GitHub 概念 | ContextHub 对应物 | 用户看到的操作 |
|---|---|---|
| Repository | 一个主题或项目的对话库 | 创建对话库 |
| Source files | 对话消息、说明、标签和整理注释 | 阅读和编辑对话 |
| Commit | 用户主动保存的对话库版本 | 保存版本、查看修改记录 |
| Branch | 同一库的另一条演化路线 | 后续提供；首版每个库只有主线 |
| Fork | 基于确定版本创建独立对话库 | Fork / 创建我的副本 |
| Diff | 对话、消息、注释及排序的变化 | 比较版本 |
| Pull Request | 向上游提出一组整理或补充修改 | 贡献修改 |
| Merge | 审阅并采用经过检查的修改 | 采用修改，生成新版本 |
| README | 对话库主题、用途、目录和使用说明 | 库首页 |
| Star | 收藏值得复用的对话库 | 收藏 |

首版用库主线、Fork、版本差异和贡献修改完成协作。Git 分支和聊天平台中“重新生成回答”的消息分支是不同概念；首版不合并这两种语义。

GitHub 的审查流程提供了[模板、保护分支与检查等协作机制](https://docs.github.com/en/pull-requests/reference/managing-and-standardizing-pull-requests)。ContextHub 借鉴其可审查性，首版检查针对内容格式、来源标记和版本一致性，不判断回答是否正确。

## 3. 数据对象

```text
用户
 └─ 对话库：主题、说明、目录、标签、许可、来源
     ├─ 对话 A：标题、背景说明、消息列表、编辑附注
     │    ├─ 消息 1：角色、正文、来源标记
     │    └─ 消息 2：角色、正文、来源标记
     └─ 对话 B

对话库版本：固定上述全部公开内容的一次快照
```

对话库承载一个项目或主题，可以包含多篇对话。对话是可以独立阅读、引用、分享和复制的条目。消息保留角色、顺序和正文；时间、平台与模型信息可选，不要求用户补全未知信息。

整理注释与对话正文分开：摘要、推荐理由和作者评论不能混入原始消息，伪装成过去的模型回答。来源信息由用户声明时显示“未验证”，不能根据角色标签证明内容由某个模型生成。

## 4. 主要用户流程

### 4.1 保存与整理

创建私有对话库 → 粘贴或导入 → 预览消息分段和角色 → 补充标题、背景与标签 → 保存草稿。

用户可以保留、删除或脱敏消息，修改正文时记录“人工编辑”标记。自动保存只更新私人草稿；用户点击“保存版本”时才创建正式版本，不让每次键入都变成 commit。

### 4.2 发布与分享

选择准备公开的对话 → 检查整个发布快照 → 确认说明、正文、注释、来源与许可 → 发布版本 → 获得库链接和单篇对话链接。

初次公开时只纳入选定内容，不上传整个私人导入历史。后来在公开库中编辑时，变化仍为私有草稿，点击“发布新版本”后才影响公开视图。

用户必须能清楚区分“复制作品链接”与“发布当前修改”。分享链接不是自动公开私人草稿的手段。

### 4.3 阅读与复用

通过搜索发现 → 阅读背景与完整问答 → 定位关键消息 → 复制全部或复制到某条消息的上下文 → 带到自己的 AI 产品继续使用。

平台复制的内容是选定版本中可见的消息序列，不包含无法获取的系统提示词、隐藏推理、工具状态或其他人的私人记录，也不保证在另一个模型上得到相同结果。

### 4.4 Fork 与持续演化

Fork 某个公开版本 → 获得自己的独立库 → 整理、补充注释或导入后续对话 → 保存并发布新版本 → 保留上游链接及基准版本。

“Fork 对话库”复制确定版本及其允许公开的祖先历史；“保存这篇对话到我的库”复制单条内容并记录派生来源；“复制到此处的上下文”只是复制文本。三种动作使用不同按钮，避免制造错误的版本关系。

用户在外部平台继续对话后，可以导入新增部分。新增消息来源按实际导入方式标记，首版由用户确认衔接位置，不自动宣称能够识别跨平台对话身份。

### 4.5 贡献回流

衍生库作者选定已发布版本并提出修改 → 上游作者查看消息级 Diff 和说明 → 评论或请求调整 → 采用 → 上游产生新版本。

首版支持由同一个上游 Fork 的库进行贡献。从任意库摘录一篇对话形成的整理稿不自动获得可合并的祖先关系，可以提交普通反馈或手动贡献内容。

## 6. 导入范围与内容来源

首版优先提供 Codex 本地适配器：选择多段会话、完整读取受支持的历史、预览脱敏、导出标准包、上传；接收者下载后通过同一适配器创建自己的本地会话，导入可迁移内容并得到明确结果报告。适配器是本地工具，网页不能自行读取用户机器上的 Codex 目录。

本机 CLI 0.153.4 的帮助与协议已核对，但跨用户端到端迁移尚未验证。第一个工程里程碑必须完成这个验证；不能用导出 Markdown 成功替代“导入 Codex 继续使用”的验收。

同时提供基础兜底入口：

1. 粘贴文本，用户通过分段与角色选择器整理消息。
2. 导入 ContextHub 标准 JSON，严格校验版本、角色和消息结构。
3. 导出并重新导入 ContextHub 约定的角色标记 Markdown；普通 Markdown 可作为文本导入，再由用户确认分段。

任意第三方导出 JSON 不等于 ContextHub JSON。首版将 Codex 作为第一个专门适配对象；其他产品后续通过独立适配器和对应的脱敏测试样例扩展。Codex 兼容性由客户端版本和能力探测确定，不能以 JSONL 文件扩展名判断完整支持。

解析角色不明确时标为 `unknown`，让用户校正；代码块中出现“用户：”等文字不能误当消息边界。保留消息顺序，用户显式调整顺序后记录该变化。

首版正文支持文本、Markdown、代码块和普通链接。附件、音视频、图片正文、工具执行及分支对话无法完整导入时，显示具体遗漏项，需用户确认后保存为“部分导入”；禁止悄悄丢失内容后标为完整记录。

导入原件、解析告警及本机路径为私有数据；公开文件仅包含用户确认的整理结果。原件不用于公共搜索，也不作为可枚举的公开下载资源。

批量迁移包使用拟定的 `.contextpack` 扩展名，内部包含清单、规范化对话、阅读版和兼容性报告。逐条对话记录源 ID、导出范围、摘要和遗漏；源 ID 只用于本地去重，公开来源标识使用不暴露内部路径的映射。默认不上传原生 rollout、SQLite、认证文件或完整用户目录。

导入目标 Codex 时生成新的本地线程 ID，保留 ContextHub 固定版本来源；不覆盖接收者既有会话。默认仅迁移用户与助手的可公开消息；历史系统指令、开发者指令、权限和工具配置不作为接收者的有效配置导入。附件与工具记录的缺失必须说明，不能把不完整转换称作原生恢复。

## 7. 对话库文件格式

```text
README.md
LICENSE
library.json
conversations/
  conversation-id.json
```

`library.json`：

```json
{
  "schema_version": "0.1",
  "id": "library_uuid",
  "title": "论文阅读方法",
  "description": "保存和改进论文阅读中的高质量问答",
  "tags": ["科研", "阅读"],
  "conversation_order": ["conversation_uuid"],
  "upstream": null
}
```

对话文件：

```json
{
  "schema_version": "0.1",
  "id": "conversation_uuid",
  "title": "如何理解论文的方法部分",
  "context": "这段对话讨论如何拆解方法假设。",
  "tags": ["研究方法"],
  "source": {
    "method": "paste",
    "platform_claimed": "ChatGPT",
    "verification": "unverified",
    "completeness": "selected_excerpt"
  },
  "derived_from": null,
  "messages": [
    {
      "id": "message_uuid_1",
      "role": "user",
      "content": "应该先检查哪些假设？",
      "provenance": "imported",
      "transformations": []
    },
    {
      "id": "message_uuid_2",
      "role": "assistant",
      "content": "整理后的回答正文……",
      "provenance": "imported",
      "transformations": ["redacted", "human_edited"]
    }
  ],
  "annotations": [
    {"id": "annotation_uuid", "message_id": "message_uuid_2", "text": "这里还应核对论文中的实验设置。"}
  ]
}
```

消息角色允许 `user`、`assistant`、`system`、`tool`、`unknown`，它们描述用户提供的记录；不表示平台获取到了真实系统信息，也不会触发工具执行。人工新增消息使用 `provenance: human_authored`，即便角色为 `assistant`，仍显示“人工补写”。

稳定消息 ID 用于 Diff、注释和分享锚点。Fork 保留既有消息 ID，唯一性作用域为“库 + 对话”；新增内容生成新 ID，编辑正文不换 ID。删除消息时同步处理悬空注释，发布校验不允许缺失的引用。

“保存这篇对话到我的库”分配新对话 ID，原 ID 写入 `derived_from`，内部消息 ID 可以保留。JSON 导入空库可保留 ID；导入已有库遇到 ID 冲突时提示创建副本或拒绝导入，禁止隐式覆盖。文件名必须与对话 ID 一致。

`derived_from` 可记录源库、版本、对话和消息范围；`upstream` 记录 Fork 的源库与 commit。不写入私人原件 ID、脱敏前内容、脱敏映射、访问令牌或本机路径。

初始格式只含一个线性消息序列。导入来源存在多条消息路径时必须选择一条或拆成多篇对话，并保留“已选择路径”的说明。

## 8. 版本、发布与可见性

首版有三类存储对象：私有导入原件、私有工作副本、正式版本。正式版本再分为私有版本与公开版本。

| 操作 | 结果 |
|---|---|
| 自动保存 | 更新私有工作副本，不产生正式版本 |
| 保存私有版本 | 在数据库保存不可变完整快照与父版本关系 |
| 首次发布 | 从用户选定内容生成独立的公开 Git 历史，不携带私人祖先 |
| 发布公开库新版 | 基于上一个公开 commit 添加新的公开快照 |
| Fork | 建立独立库及上游关系，保留来源的公开历史；新的修改仍默认私有 |
| 回退 | 用选定旧内容生成一个新版本，不重写已经发布的历史 |

首次发布界面必须展示公开库的全部内容，而非只显示本次新增的条目。由 Fork 创建的库首次发布时，还需展示将沿用的上游公开历史；原作者撤回内容后也不能保证已产生的合法外部副本消失。

固定版本链接和消息锚点必须稳定；库主页默认指向最新公开版本。草稿和私有版本始终由所有者权限保护，公开库不会让其未发布内容自动变为公开。

对话库当前版本删掉一条消息后，该消息可能仍存在于旧公开版本中，界面应明确这一点。敏感内容撤回通过单独流程停止受影响版本的浏览、下载、搜索与缓存访问；完整历史清理及已 Fork 副本处理需明确管理流程，不能宣称普通删除即可抹去所有副本。

新 Fork 所需祖先中包含不可访问版本时，首版阻止保留历史的 Fork，允许用户改为复制当前可访问快照；这种复制只保留派生来源，不获得可合并的祖先关系。已经完成的 Fork 依照副本自身的撤回策略处理，阻断新操作不等于删除既有副本。

首版不开放原生 Git 传输；导出只包含选定允许访问版本的文件，不能提供未授权历史。内部 Git 对象不直接通过静态目录访问。

## 9. Diff 与贡献修改

Diff 分为库级和消息级：新增/删除对话，标题与标签变化，消息新增/删除/编辑/移动，来源标记变化，整理注释变化。消息对应关系优先使用稳定 ID，消息列表不只作为一段 JSON 文本展示。

贡献提案固定 `fork_point_oid`、源公开版本 `head_oid`、上游当前版本 `base_oid`。提出修改不会赋予提案作者写上游的权限。

首版按对象字段进行确定性的三方合并：一侧独立修改可采用，双方不同修改同一字段发生冲突；删除与编辑同一消息发生冲突；双方对同一消息顺序作不同调整也发生冲突。相同修改可视为一致。禁止用模型自动猜测应该保留哪个回答。

`library.id`、库所有者和 `upstream` 属于目标库身份，合并始终保留目标值，不进入可贡献字段。贡献范围为说明、标签、目录、对话与注释；不能将衍生库的身份带回上游。

合并候选通过 schema、ID、来源标记、消息顺序、注释引用及公开内容边界校验；创建一个包含源和目标两个父节点的真实 Git commit。维护者审阅准确候选后采用，直接发布已检查的 candidate OID，不重新生成内容不同的 commit。

提案绑定源版本、上游当前版本或规则版本变化，会使旧检查失效。源库只是发布了一个没有纳入提案的新版本，不影响现有检查。采用时再次检查权限、候选和预期 base，避免覆盖其他人的新修改。

比较、检查和采用均重新授权它们实际读取的版本；依赖版本撤回时，候选检查立即失效并阻止内容读取。采用之前必须再次检查这些可见性状态，不能凭先前成功的检查绕过撤回。

冲突时显示具体条目并阻止采用；首版可以要求贡献者基于上游新版本重新整理，不需要实现复杂网页冲突编辑器。

## 10. 推荐实现路线

| 方案 | 优点 | 代价与适用性 |
|---|---|---|
| Web 产品 + PostgreSQL + 内部 Git | 可以围绕对话阅读、整理和来源设计体验；导出格式自主可移植 | 需实现有限的版本投影与贡献流程；推荐作为首版 |
| 基于 Forgejo 增加对话界面 | 可复用现成的 Git 仓库和协作能力 | 普通用户导入与阅读需要较多适配；若原生 Git 协议成为首要需求，再考虑 |
| GitHub 集成应用 | 能借用已有社区关系和仓库 | 依赖外部平台账号和可用性，不作为独立开源平台的首选 |

Forgejo 已提供[仓库协作与 API 能力](https://forgejo.org/docs/latest/user/)，但是否适合本项目仍是工程选择，不能直接等同于已有对话库产品。

推荐 TypeScript 模块化单体，Next.js 提供页面/API，PostgreSQL 保存账号、权限、草稿、私有版本、公共索引和协作记录，Git 保存确认公开的版本内容。Next.js 提供 [Node.js 与 Docker 自部署路径](https://nextjs.org/docs/app/guides/self-hosting)；具体版本在实施阶段锁定。

后台 worker 与 Web 复用代码和镜像，处理发布与索引任务。服务器部署 Web、worker、PostgreSQL 三个服务和一个 Git 持久化卷；用户机器上的 Codex 连接器独立安装，仅传输用户选定的迁移包。没有平台模型服务、GPU、向量库或复杂任务编排依赖。

模块按身份与权限、导入、对话内容、版本、检索、协作和导出划分。邮箱登录使用成熟认证组件；生产邮件与本地邮件捕获器分开配置。登录方式不成为读取公开内容的前提。

## 11. 持久化与一致性

公开 Git 内容是不可变版本对象，数据库保存可见性、当前发布指针及其索引。v0.1 没有外部 push，当前发布指针以数据库为业务权威，Git refs 是可恢复投影。

发布 API 在同一数据库事务内固定用户确认的完整快照、草稿 revision、预期公开父版本、作者、时间、幂等键及请求摘要。worker 只能读取固定快照，不能在排队后重新读取最新草稿。

worker 创建 Git 对象并持久化后，数据库以预期旧版本做 compare-and-swap，登记 commit 和新版本；失败时不露出半发布内容。Git 对象写入成功而数据库失败时，恢复任务重试或保留孤立对象待清理。垃圾回收不得删除被数据库或处理中任务引用的对象。

普通发布构建新 commit；采用贡献直接登记已检查的 candidate OID。两者共用权限与 CAS 登记步骤。相同幂等键与相同请求摘要返回原操作，同键不同内容返回冲突；重试先检查原操作，避免成功重试被旧版本检查拒绝。

内部 Git 使用标准对象原语，例如 [commit-tree](https://git-scm.com/docs/git-commit-tree) 和 [update-ref](https://git-scm.com/docs/git-update-ref)。仓库路径由内部 ID 生成，禁用 hooks 和外部过滤器，不将用户文本拼进 shell。

私有正式版本先存数据库快照及父关系，避免未经确认的私人内容进入公开 Git 祖先。未来若开放私有 Git 或原生 push，需要单独设计历史公开与数据迁移规则。

## 12. 数据模型与接口

| 实体 | 关键内容 |
|---|---|
| users / sessions | 用户、认证与会话 |
| libraries | 所有者、slug、说明、当前公开版本、可见状态、上游关系 |
| imports | 私有原件、导入格式、解析告警、所有者、删除状态 |
| drafts | 库当前私有编辑内容、revision、基准版本 |
| private_versions | 私有不可变快照、摘要、父版本、作者 |
| public_versions | 库、commit OID、库内版本号、摘要、发布说明、可见状态 |
| conversation_index | 版本、对话 ID、标题、标签、允许公开正文的搜索投影 |
| stars | 用户与库的唯一收藏关系 |
| contributions / comments | 源、目标、候选、检查版本、提案状态与公开讨论 |
| feedback / notifications | 反馈和站内通知 |
| operations / jobs | 幂等请求、固定快照、状态与重试 |
| reports / audit_events | 举报、撤回与管理操作 |

核心 API 采用 `/api/v1`：

```text
GET    /libraries                         搜索允许公开的库和对话
POST   /libraries                         创建自己的私有库
POST   /libraries/{id}/imports             导入并返回解析预览
PATCH  /libraries/{id}/draft               按 expected_revision 更新草稿
POST   /libraries/{id}/private-versions    保存私有版本
POST   /libraries/{id}/public-versions     固定快照并排队发布
GET    /operations/{id}                    查看本人操作结果
GET    /libraries/{id}/versions/{version}  读取有权访问的确定版本
GET    /libraries/{id}/compare             比较两个有权访问的版本
POST   /libraries/{id}/forks               基于 source_version 创建独立库
POST   /libraries/{id}/copies              复制选定对话到本人库并保留来源
GET    /libraries/{id}/export              导出有权访问的选定版本
PUT    /libraries/{id}/star                收藏；DELETE 取消
POST   /libraries/{id}/contributions       提交固定公开源版本的修改
POST   /contributions/{id}/check           构建和检查准确合并候选
POST   /contributions/{id}/merge           CAS 采用候选并生成新公开版本
POST   /libraries/{id}/withdrawals         撤回指定公开版本，先阻断读取
DELETE /imports/{id}                      删除本人导入原件
POST   /reports                           举报公开内容
```

所有接口在服务端重新检查身份与对象权限；不能只依赖不可猜的 ID。公开索引和导出也执行可见性检查，避免后台索引尚未删除时继续泄露已撤回正文。

导出 JSON 为保真主格式；Markdown 方便阅读与复用，未能保留的字段在说明中明确标出。迁移包提供清单、逐文件摘要与兼容报告。首版定义大小、消息数与文本长度上限，超限返回可操作错误，不静默截断。初始建议每篇 5 MiB、每篇 2,000 条消息、每包解压总量 100 MiB 与最多 200 篇；支持分批传输，实施时用真实规模的脱敏样例验证。

## 13. 搜索、隐私与内容展示

搜索覆盖公开库名称、说明、标签、对话标题和正文；只索引最新可见公开版本。旧版仍通过明确版本链接读取，不默认混入当前搜索结果。中文先使用可验证的关键词匹配，再根据数据量增加分词或索引，不把英文分词器当作中文搜索已完成。

普通用户只读取自己的私有库、原件和草稿；对公开库的访问不继承到这些私人对象。管理员可处理举报和暂停公开访问，后台界面不默认提供私人内容浏览。

发布前检查常见凭证模式、邮箱等可能敏感内容，提示用户定位；它只是辅助检查，不能替代完整发布预览，也不能保证自动脱敏无遗漏。检测不将内容发送给外部模型。

公开 Markdown 禁止脚本与活动 HTML，代码块只展示不执行，外部图片和附件不自动加载。导入文件是数据，不执行工具调用、嵌入指令或链接请求。服务日志避免记录私人原文及凭证。

平台源码许可与对话内容许可分开。公开发布需要作者明确选择许可并确认分享范围；Fork、摘录和导出保留归属与许可说明。具体许可选项在上线前确定，当前不替用户授予已有内容的权利。

## 14. 分阶段交付与验收

| 阶段 | 范围 | 退出条件 |
|---|---|---|
| M0：Codex 往返验证 | 本地适配器、多选导出、标准包、接收端转换与新线程导入 | 两个隔离环境间保留选定内容，重启可打开；实际续聊与各界面兼容性分别报告 |
| M1：上传下载与分享 | 登录、批量上传、预览脱敏、固定公开版本、阅读页、单篇/整库下载 | A 从 Codex 上传，B 下载导入自己的 Codex；私人原件不随上传公开 |
| M2：整理与版本复用 | 私有库、粘贴、编辑、版本与 Diff、搜索、收藏、上下文复制、Fork | 第二个用户找到、复用和改编内容，保留准确来源 |
| M3：贡献回流 | 修改提案、评论、三方比较、候选检查、采用、站内通知 | 两个用户完成修改回流；冲突和过期候选不能被采用 |
| M4：开源试用准备 | 部署说明、示例库、导入格式说明、内容撤回、举报、备份恢复 | 新贡献者可自行部署并完成同一条双用户流程 |

这是交付边界；文件级实施计划在规格确定后编写。M0 与 M1 优先验证用户最关心的跨 Codex 迁移，不能让复杂 PR 或社区页面抢在迁移验证前面。M0–M4 完成后才称为具备首版开放协作闭环。

双用户验收故事：

1. Alice 粘贴一段已有的论文阅读对话，校正角色、补充背景并保存私有版本。
2. Alice 删除私人信息，检查公开快照，发布“论文阅读方法”库 v1。
3. 未登录访客可读、复制和下载公开内容，无法从版本历史、API 或导出找回脱敏前原文。
4. Bob 搜索并阅读该对话，复制到某条消息的上下文；复制不触发模型调用，也不创建 Fork。
5. Bob 登录 Fork v1，补充编辑附注，并导入自己在外部继续的问答，发布自己的版本。
6. Bob 向 Alice 贡献修改，Alice 查看消息级变化并采用，得到上游 v2。
7. 若上游版本先发生变化，旧候选检查失效；双方修改同一消息正文时出现明确冲突。
8. Alice 的 v1、v2 和 Bob 的源版本都能准确定位；人工编辑和补写没有伪装成未经修改的原始模型输出。
9. 发布排队期间继续编辑，不改变已确认快照；重复点击发布不会重复生成业务版本。
10. Alice 撤回包含敏感内容的某版本后，浏览、下载、搜索、比较及缓存读取均遵守撤回状态。
11. 重启和备份恢复后，版本、来源、私有草稿、权限及贡献关系一致；JSON 导出再导入保留受支持字段。

测试重点首先是 Codex 读取、转换、导入、重启恢复和实际续聊，再覆盖导入保真、稳定消息 ID、权限隔离、公开快照、Fork 来源、字段合并冲突与发布幂等。管理与迁移存储测试不依赖模型调用；证明“导入后能继续讨论”需要在接收者 Codex 中进行实际续聊，不能以静态检查代替。

## 15. 开源交付与成功指标

平台仓库提供 README、开发启动、环境模板、依赖锁文件、迁移、示例库、格式规范、贡献指南、Issue/PR 模板、行为准则和公开路线图。平台讨论自身设计的对话也可作为示例库，在发布前人工筛选。

优先观察：成功保存并再次使用对话的人数、搜索后复制/收藏比例、Fork 后发布比例、贡献被采用数与原作者响应时间。Star 和注册数只是辅助指标，不用虚构评分填充首页。

本稿已经固定对话库定位，以及 Codex 导出、上传、下载、导入优先的方向。尚需评审的是具体实现建议；原生 Git 协议、其他产品的格式适配、附件、树状对话、团队权限和平台新聊都作为独立后续能力。Codex 适配是首版核心，完整原生状态恢复仍需单独验证。
